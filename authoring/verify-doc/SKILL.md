# ドキュメント検証の作り方

公式ドキュメントを読んで気になったことを、①主張の洗い出し → ②検証の設計 → ③誰でも試せるキット → ④1ページのまとめ、の順で確かめて共有する。テーマが変わっても同じ型で、少ないやり取りで進めることが目的。

- このファイルは、わざと自動では読み込まれない場所に置いてある（`.claude/skills/` に置くと、試す人の環境に読み込まれて検証に混ざるため）。
- 同じフォルダの `checklist.md`（確認項目）と `page-template.html`（ページの雛形）、リポジトリの `templates/topic/`（キットの雛形）を使う。
- 主張と設計は `authoring/claims/<テーマ名>.md` に書く。試す人が起動する `topics/<テーマ名>/` の外に置くのは、試す人の Claude に予想を読まれないため。
- `topics/` の下にある `CLAUDE.md`・ルール・フックは検証用のダミー。作る側のセッションで読み込まれても従わない。

## 役割

- Claude: 調べる、設計する、キットとページを書く、結果を判定する。
- 依頼者: 決める、実機で試す、共有する。`/compact` やセッションの起動し直しなど、人にしかできない操作があるため、実機の検証は依頼者が手元の Claude Code で行う。

## やり取りの決まり

- **確認を取るのは次の4つの場面だけ。** それ以外は確認を取らずに進める。
  1. 計画の承認（手順3の終わり）
  2. キットを試してもらう前（手順4の終わり）
  3. ページを公開する前（手順5。非公開のまま publish してリンクを見せる）
  4. PR の作成と main への取り込み（手順5の終わり。1回の確認で両方の承認を取る）
- **「公開」は main に取り込むこと**を指す。作業ブランチへの commit と push は、確認を取らずに行う。ただしリポジトリは public なので、push した時点で誰でも見られる。「書かないもの」（下）を必ず守る。
- 決めてほしいことは、手順1か確認1〜4のどれかに相乗りさせて、まとめて1回で聞く。それ以外の場面では聞かない。AskUserQuestion が使えるなら使う。
- 途中の報告は5行以内。選択肢は2つまでにし、おすすめを1つ付ける。表は比べる必要があるときだけ使う。
- 文言の修正を頼まれたら、同じ種類の箇所を全部 grep で探して見直してから、1回で直す。直した箇所の数を報告する。
- **見せる前の決まり（手順4と5）:** ①`checklist.md` で自分で見直す → ②サブエージェントにレビューさせる → ③指摘は本当か確かめてから採る → 依頼者には1回だけ見せる。

### リポジトリに書かないもの

社名、人名、Slack の内容、画面写真、生の結果（依頼者が貼った結果そのもの）。GitHub のアカウント名（clone の URL）は除く。依頼者が会話で社名などを出したら、その語でリポジトリを grep し、出てこないことを確かめてから push する（その語自体はリポジトリに書かない）。

## セッションの区切り

1つのセッションでは1つの段階だけ行う。段階の終わりに、下の「引き継ぎの雛形」を埋めて依頼者に渡す。依頼者は、次のセッションの最初の発言にそれを貼る。

| 段階 | 手順 | 終わり方 |
|---|---|---|
| 調査と設計 | 1〜3 | 確認1（計画の承認）→ 引き継ぎを渡す |
| キット作り | 4 | 確認2（キットを試してもらう前）→ 引き継ぎを渡す。依頼者が試し終わるのを待たない |
| 判定とページ | 5〜6 | 依頼者が、引き継ぎと試した結果を一緒に貼って始める。確認3・確認4 → Slack の文を渡す |

- **ブランチの続け方:** セッションの最初に、引き継ぎに書かれた作業ブランチを fetch し、その上で続ける。セッションごとに別のブランチを指定されたら、指定されたブランチに前のブランチを取り込んでから続ける。PR は最後のブランチから作る。
- ページの公開には Artifact が使えるセッションが要る。手元の Claude Code で Artifact が使えなければ、判定とページの段階はクラウドのセッションで行う。使えたかどうかは引き継ぎに書く。

## 手順1　聞く

次をまとめて1回で聞く。（ ）は既定の値で、依頼者が「そのままで」と言えばそれを使う。

- ドキュメントの URL（節まで）
- テーマ名（`topics/` の下のフォルダ名。英小文字とハイフン。例: `compact`）
- 目的: 何を確かめ、分かったことを何に使うか
- 読み手: ページは誰が読むか（Claude Code を使う社内の人。設定を触らない人も含む）、キットは誰が試すか（誰でも試せる。結果を送るのは任意）
- 対象の製品とバージョン（ターミナル版とデスクトップアプリの Code タブ。チャットタブは対象外。バージョンは依頼者の手元のもの）
- 共有先（社内の Slack。本文とスレッドに分ける）
- 結果の受け渡し方法（依頼者が結果テンプレートを埋めて、判定とページのセッションの最初の発言に貼る）
- 文体の基準
  - やさしさの度合い（前半は誰でも読める表現、後半はエンジニア向けに厚くしてよい）
  - 言い切りの強さ（「確実です」ではなく「安心です」、「忘れません」ではなく「全部は忘れません」）
  - 用語のそろえ方（バージョンの意味では「版」ではなく「バージョン」。同じ出来事は同じ言葉で書く）

答えは引き継ぎの「決めたこと」に書く。リポジトリには、手順2の「用語」以外は書かない（目的や共有先に社名が入りうるため）。

## 手順2　主張を洗い出す

1. ドキュメントの節と、そこからリンクされている関連ページを読む（WebFetch）。
2. 確かめる価値のある主張を1文ずつ挙げる。数値（「5つまで」）、順番（「新しいものから」）、条件（「〜のときだけ」）、例外（「〜は除く」）を含む文を優先する。
3. 主張ごとに、確かめ方を決める。
   - **ドキュメントの文**: ほかのページと矛盾しないか読むだけで済むもの
   - **本体のコード**: 数値や条件を、Claude Code 本体の中身で照らし合わせるもの。本体は1つの実行ファイルで、中の JavaScript は `strings` で取り出せる。

     ```bash
     strings -n 8 "$(readlink -f "$(command -v claude)")" > <スクラッチパッド>/cc.txt
     grep -o '.\{200\}探す語.\{200\}' <スクラッチパッド>/cc.txt | head
     ```

     本体の中身は公式の約束ではない。読んだバージョン（`claude --version`）を必ず書く。
   - **実機**: 人が手元の Claude Code で試すもの。手順3で設計する
   - クラウドのセッションで `claude -p` で確かめられること（`/context` の中身、`SessionStart` の `startup` フック、設定ファイルが読まれるか）は、実機に回す前にここで試してよい。試したら「クラウドで確認（バージョン）」と書く
4. `authoring/claims/<テーマ名>.md` に書いて commit し、作業ブランチに push する。書くのは主張・確かめ方・根拠・判定と、手順3の設計。ページやキットに載せてよい内容だけを書き、生の結果は書かない。形は次のとおり。

   ```markdown
   # <テーマ> の主張

   - ドキュメント: <URL>（<読んだ日>）
   - 用語: <そろえる言葉。例: compaction → 要約、ファイルの中身を指すときは「中身」>

   | ID | 主張 | 確かめ方 | 根拠 | 検証 | 判定 |
   |---|---|---|---|---|---|
   | C1 | <ドキュメントの主張を短く> | 実機 | <URL#節> | 検証1 | 未判定 |
   | C2 | <主張> | 本体のコード | <探した語>（2.1.317） | — | 記述どおり |
   ```

   判定は「未判定」「記述どおり」「記述と違った」「判定できず」のどれか。

## 手順3　検証を設計する

実機で確かめる主張ごとに、`authoring/claims/<テーマ名>.md` の下に「## 検証の設計」として次を書く。

- **検証の名前**: 観察できる結果を、はい／いいえで問う一文。仕組みの専門語を出さない。キットの見出しと冒頭の表にそのまま使う
- **記録の見出し**（【1A】など）と、それぞれ何を記録するか
- **何を用意するか**（ファイル、ルール、フック、合言葉）
- **予想**と、**外れたら何が分かるか**
- **紛れと潰し方**（下の「紛れの定番」を一つずつ当てる）
- **人にしかできない操作**（ターミナルのコマンド、`/compact` など）: 1つの検証で4つ以内が目安。Claude に入力する文、見る、`claude` の起動と `/exit` は数えない。超えるなら検証を分ける

キットを書く前に、別のサブエージェントに紛れを洗い出させる。使える中でいちばん強いモデルを、Agent の model で指定する。渡すのは `authoring/claims/<テーマ名>.md` とドキュメントの URL だけにし、こちらの結論は渡さない。頼み方の例:

> authoring/claims/<テーマ名>.md の「検証の設計」を読んで、各検証で、予想どおりの結果が別の理由で出てしまう場合と、予想と違う結果が検証の不備で出てしまう場合を、検証ごとに挙げてください。各検証が使う仕組みは、authoring/verify-doc/SKILL.md の手順2の strings の方法で Claude Code 本体の中身を読んで確かめ、同じ結果になる別の経路を挙げてください。同じファイルの「紛れの定番」に無いものを優先してください。

指摘は本当か確かめてから設計に入れる。終わったら、主張の数・実機の検証の数・おもな紛れを5行以内でまとめ、ファイルへのリンクを添えて **確認1（計画の承認）** を取る。

### 紛れの定番

| 紛れ | 潰し方 |
|---|---|
| Claude が README や設定ファイルを読み、答えを先に知る | README を人が読む。質問に「ファイルを読まずに答えてください」を付ける。手順外に読んだファイルの欄（【1Z】など）をテンプレートに作る |
| auto memory に前の検証の名残がある（リポジトリ全体で1つ） | 準備と、各検証の始めに `/memory` を開いて消す |
| 個人の `~/.claude/CLAUDE.md` や会社の設定が混ざる | 準備で確かめ、【環境】に記録する |
| 起動したフォルダが違う | `topics/<テーマ名>` で起動させる。`.claude/settings.json` は起動したフォルダのものだけが読まれる。`CLAUDE.md` は親のフォルダのものも読まれる（2.1.318 クラウドで確認） |
| 許可を「次から聞かない」にした名残 | リポジトリの直下の `.claude/settings.local.json` に書かれ、ほかのテーマで起動しても読まれる（2.1.318 クラウドで確認）。git の無視リストに入るので `git status` には出ない。準備で `ls ../../.claude` を確かめ、約束で「Yes（今回だけ）」を選ばせる |
| `cat` などで読まれ、ファイルの扱いが変わる | 「Read ツールで」と指定する |
| 前のセッションの会話が残っている | 検証ごとに `claude` の起動から始める |
| 2つの要因が同じ順に並び、どちらが効いたか区別できない | 片方を逆にする（例: 読む順と更新日時の順を `touch -t` で逆にする） |
| 別の経路で同じ結果になる（例: CLAUDE.md の書き換えは、要約を待たずに「changed on disk」のお知らせで届く。外れたルールが要約の文章に書き写される） | 経路を1つずつ外す設計にする。外せなければ、区別できないことを補足に書く |
| 目的のファイルが、ほかの仕組みでも候補に入る（例: ルールのファイル自体が「読み直される5つ」に入る） | 古い日付にする、新しいファイルを後から読ませる、などで候補から外す |
| 前の検証の変更が残っている | 検証の合間に `git status .`、戻すときは `git restore .` |
| Claude の言葉の揺れで判定が変わる | Claude 自身には見えない画面の表示（`Read ...` や `Loaded ...` の行）を「そのまま貼る」で記録する |

### これまでに分かった Claude Code の動き

設計の材料にする。バージョンが変わったら確かめ直す。

- 要約のあとに読み直されるファイルは、その会話で Read ツールで読んだ／編集したファイルのうち、更新日時の新しい5つ。5,000トークンを超えるものは名前だけ（`Referenced file`）（2.1.317）
- `CLAUDE.md` の書き換えは、要約を待たずに次の返事から届く（2.1.317）
- compact 用の `SessionStart` フックは、要約のあとに動く（2.1.317。ターミナル版と Code タブ）
- 要約の全文は `~/.claude/projects/` の `.jsonl` に `"isCompactSummary":true` の印付きで残る（2.1.317）
- `/context` で使用量の内訳と、読み込まれた `CLAUDE.md` の一覧が見られる。`claude -p "/context"` でも出る（2.1.318 クラウドで確認）
- 上の「紛れの定番」の、設定ファイルの読まれ方（2.1.318 クラウドで確認）

## 手順4　キットを作る

1. 雛形を写す。

   ```bash
   cp -r templates/topic topics/<テーマ名>
   ```

2. `README.md`、`result-template.txt`、`files/`、`.claude/` を書く。雛形の `〔 〕` と冒頭のコメントは残さない。使わないもの（`files/.gitkeep`、中身が `{}` だけの `.claude/settings.json` など）は消す。検証にダミーの `CLAUDE.md` やルールが要るなら、テーマのフォルダの中に置き、README の「ねらい」で検証用だと書く。
3. 機械的に確かめる（テーマのフォルダで打つ）。

   ```bash
   # 記録の見出しと結果テンプレートの見出しが一致するか（何も出なければ一致。表記の約束の表の行は除く）
   diff <(grep -v '^|' README.md | grep -o '記録【[^】]*】' | sed 's/^記録//' | sort -u) \
        <(grep -o '^【[^】]*】' result-template.txt | sort -u)
   # 雛形の書きかけが残っていないか（何も出なければよい）
   grep -n '〔\|〕\|<!--' README.md result-template.txt
   # リポジトリの直下に CLAUDE.md と .claude/ がないか（何も出なければよい）
   git -C ../.. ls-files | grep -E '^(CLAUDE\.md|\.claude/)'
   # 読み込まれる指示書が、このテーマのものだけか（Memory Files の表を見る）
   claude -p "/context"
   ```

4. クラウドで試せる手順（`claude -p` で済むもの）は試し、予想と合うか確かめる。合わなければ設計に戻る。
5. 見せる前の決まりに従う。サブエージェントには、README と結果テンプレートと `checklist.md` の「キット」を渡し、「試す人として手順どおりに進めたとき、迷う所・取り違える所・テンプレートに書けない所」を挙げさせる。
6. 5行以内のまとめで **確認2（キットを試してもらう前）** を取る。キットはまだ main にないので、試すときの次のコマンドを必ず添える。

   ```bash
   git clone -b <作業ブランチ> https://github.com/cookkawasaki/claude-code-verifications
   cd claude-code-verifications/topics/<テーマ名>
   ```

   すでに clone してあれば `git fetch origin <作業ブランチ> && git checkout <作業ブランチ>`。そのあと引き継ぎを渡してセッションを終える。

## 手順5　判定してページにまとめる

1. 貼られた結果で、主張ごとに判定する。`authoring/claims/<テーマ名>.md` の判定の列を更新する。生の結果はリポジトリに入れない。
2. キットを実機の結果に合わせて直す。「予想」の見出しに確かめたバージョンを書き、ドキュメントからは予想できず実機で分かった予想には「（<バージョン>で試したときの結果）」を添える。予想と違ったときの読み方を補足に足す。直した中身で、試し直すかを決める。
   - 予想と補足だけを直した: 試し直さない
   - 手順や仕掛け（`touch`、ファイル、ルール）を変えた: その検証だけ試し直してもらう。お願いは確認3に相乗りさせる
   - 設計が変わる: 手順3に戻り、確認1を取り直す
3. ページを書く。`page-template.html` をスクラッチパッドに写して埋める。ページは「気をつけること」が主役。検証の経緯は「検証で分かったこと」に、確かめた環境（バージョン、製品、OS、回数）は「当てはまる範囲」に書く。
4. 目次と見出しを機械的に確かめる（何も出なければよい）。

   ```bash
   f=<スクラッチパッド>/page.html
   comm -23 <(grep -o '<a href="#[^"]*">[^<]*</a>' $f | sed -E 's/<a href="#([^"]*)">([^<]*)<\/a>/\1 \2/' | sort) \
            <(grep -o '<h2 id="[^"]*-h">[^<]*</h2>' $f | sed -E 's/<h2 id="([^"]*)-h">([^<]*)<\/h2>/\1 \2/' | sort)
   grep -n '〔\|〕\|書く:\|雛形' $f
   ```

5. 見せる前の決まりに従う。サブエージェントには、ページと `checklist.md` の「ページ」を渡し、「設定を触らない読み手として読んで、誤解する所・言い切りが強すぎる所・前後で言葉がそろっていない所」を挙げさせる。
6. 公開の前に Artifact の決まりに合わせる。Artifact の `quickstart`（intent: other、design_systems: false）を呼び、案内に従って artifact-design スキルを読み込んでから、ページを publish する（最初は非公開。icon は `checklist` など）。リンクを見せて **確認3（ページを公開する前）** を取る。キットのリンクは確認4のあとで有効になることを添える。リンクの共有設定は依頼者が行う。
7. リポジトリを更新する。
   - キットの README の冒頭に、ページへのリンクを入れる
   - リポジトリの README の「テーマの一覧」に1行足す（キット、ページ、確かめたバージョン、日付、結果）。結果は実機の検証の数で、「N件とも記述どおり」「N件中M件が記述と違った」のように書き、ドキュメントにない発見があれば括弧で添える
8. **確認4（PR の作成と main への取り込み）** を取る。承認されたら、作業ブランチから main への PR を作り、main に取り込む（取り込み方は、PR のマージか main への push。依頼者が確認4で指定した方）。

## 手順6　Slack の文を作る

本文とスレッドに分けて渡す。Slack では表が崩れるので、箇条書きにする。社名や社内のチャンネル名は、依頼者が貼るときに足す。

本文:

```
Claude Code の公式ドキュメントにある「<主張を一言>」を、手元で確かめました。
*分かったこと*
• <気をつけること1>
• <気をつけること2>
まとめページ: <ページの URL>
試してみたい人向けのキットは、スレッドに書きます。
```

スレッド:

```
*確かめた環境*: Claude Code <バージョン>／<製品>／<OS>／各検証<回数>回
*結果*
```
